# 模块化编码规则

本文适用于有明确边界和使用者的代码单元，包括 JS/TS 模块、前端功能、Node 工具、SDK、业务功能包、适配层、内部库和长期维护脚本。

它不是语言语法规范，也不是格式化规范。它只约束一件事：模块如何划分、如何暴露 API、如何管理状态、如何扩展、如何验证、如何清理旧入口。

## 1. 适用范围

### 1.1 什么时候必须按本文处理

一段代码满足任一条件，就按模块处理：

- 被多个地方调用，或未来明确会复用。
- 有公开导出、配置对象、上下文对象、adapter、注册表或生命周期。
- 持有状态、缓存、偏好、运行态或外部资源。
- 连接多个模块、数据源、平台或运行环境。
- 修改它会影响其它调用者的理解成本。
- 包含 README、demo、公共类型或对外示例。

一次性小函数不强行套完整模块结构，但仍必须遵守命名准确、状态来源唯一、边界清晰三条底线。

### 1.2 设计顺序

生成、实现或重构模块前，先按顺序确认：

1. **职责**：模块负责什么，不负责什么。
2. **使用者**：谁调用它，最常见用法是什么。
3. **入口**：公开 API 是否足够少、稳定、好记。
4. **依赖**：模块可以依赖谁，禁止依赖谁。
5. **状态**：唯一真实状态在哪里，哪些值必须派生。
6. **配置**：配置入口、默认值、覆盖顺序和可序列化边界是什么。
7. **扩展**：扩展点、优先级、adapter 和回调契约是什么。
8. **删除**：旧入口、旧类型、旧文档和旧 demo 是否同轮删除干净。
9. **验证**：如何证明默认路径、扩展路径和错误路径符合预期。
10. **文档**：哪些规则必须同步到 README、设计说明、规则文件或注释。

不要先写实现，再用补丁字段解释设计。

### 1.3 成功标准

一个模块完成后，至少应满足：

- 使用者能从公开入口完成常见用法，不需要阅读内部源码。
- 默认路径足够短，高级路径显式进入，不污染普通使用者。
- 公共类型、运行时代码、示例和文档表达同一套契约。
- 内部实现可以复杂，公共入口必须少而清楚。
- 状态、配置、扩展和副作用都有唯一可信来源。
- 旧入口、旧类型、旧文案、旧 demo 和旧注释没有残留。

## 2. 边界与依赖

### 2.1 模块边界

- 模块必须声明输入、输出、状态所有权和副作用边界。
- 基础模块只能依赖框架、标准库、自身内部模块和显式传入的接口。
- 基础模块禁止直接依赖具体业务 Store、业务 API、业务页面、业务入口配置或具体业务单元。
- 跨模块协作使用 `context`、`options`、`config`、adapter、注册表、事件或显式 action，不互相硬 import。
- 上游模块负责过滤、鉴权、预处理和环境差异；下游可复用模块只消费整理后的输入。
- 依赖方向必须稳定：底层模块不能反向知道上层模块，通用模块不能知道具体业务模块。
- 发现循环依赖时，优先抽出接口、adapter 或事件，不靠挪 import 路径掩盖问题。

### 2.2 公开与内部

- 模块必须区分公开 API 和内部实现。
- 使用者只能从公开出口导入，例如 `index.ts`、`index.js` 或包入口。
- 内部目录、内部文件名、内部常量和内部协议字符串不能成为使用者契约。
- 公共出口只导出使用者需要稳定依赖的内容，越少越好。
- 内部实现可以拆得细，公共出口必须收得紧。
- 内部实现不要从公共出口绕回引用自身。
- 某个内部能力开始被多个外部使用点直接导入时，要提升为正式公共 API，或提供更高层 helper。

### 2.3 目录与入口

- 入口文件保持薄，只表达装配关系、主出口和必要元信息。
- 复杂功能的内部组合、映射关系和运行时配置放在功能目录内。
- 全局入口只负责依赖注入、全局能力注册、全局错误处理和主出口等壳能力。
- 不通过名称特判权限、样式或业务行为；使用配置、元信息或 adapter 表达。
- 文件组织服务边界，不服务个人阅读习惯；同一职责放一起，不同层级不要互相穿透。
- 只创建实际需要的目录和文件，不生成空架子。

推荐目录含义：

```txt
module/
├── index.*     # 公共出口
├── core/       # 当前主设计
├── adapters/   # 外部能力适配
└── runtime/    # 生命周期和副作用
```

目录规则：

- `core/` 表达当前主设计，不能混入旧 API 判断。
- `adapters/` 只负责把外部能力转成模块契约，不承载核心业务规则。
- `runtime/` 只放生命周期、副作用编排和运行态协调，不放纯类型或纯配置。
- 小模块可以不拆目录，但仍要保持公共出口、核心逻辑和适配逻辑边界清楚。

## 3. 使用者接口

### 3.1 公共 API

- 公共 API 面向使用者意图命名，不表达内部实现形态。
- 公共 API 优先对象化，使用 `context`、`options`、`config` 等对象承载能力。
- 禁止长期维护一串零散参数、零散回调或零散状态字段。
- 新增能力优先扩展已有对象，不轻易新增平行顶层字段。
- 高频能力可以直接挂在对应领域对象下，不要为了“分层”再包无意义的 `actions`、`state` 或中转层。
- 默认用法必须短；高级用法可以长，但必须可读。
- 公共 helper 只用于隐藏内部 key、重复映射、默认组合和易错样板。
- helper 不能变成另一套并行配置语言。
- API 的返回值、错误行为、同步或异步、是否可取消必须明确。

推荐：

```ts
createFeature({ source, adapters })
```

不推荐：

```ts
createFeature(source, onOpen, onClose, adapter)
```

### 3.2 契约与类型

- 公开输入、输出、错误和事件都必须有明确契约。
- 不把第三方返回、宿主实现或临时内部结构直接暴露成公共契约。
- 可选字段必须说明默认值、缺省语义和是否会被持久化。
- 外部原始数据必须在边界处归一化，模块内部只消费稳定结构。
- 契约变化必须说明新入口、旧入口删除范围和验证方式，不能只靠类型报错让使用者猜。
- 公共类型应从稳定类型入口导出，不暴露内部渲染中间态或临时结构。

### 3.3 配置设计

- 使用者能用对象配置表达的能力，不新增函数式 DSL。
- 同一类配置只能有一个声明入口。
- 已有对象能承载语义时，不新增平行字段。
- 对象内部使用结构化配置，不把有层级关系的能力压平成一堆字段。
- 不引入无意义中间层；中间层必须有真实领域语义。
- 默认配置必须可用，普通使用者不应为了默认能力写大量配置。
- 远程配置、后端下发配置和可持久化配置必须保持可序列化。
- 运行时对象、函数和类实例通过注册表或 adapter 映射，不直接塞进需要序列化的配置。
- 配置覆盖顺序必须固定并写清楚，不能靠实现细节猜。

推荐：

```ts
feature: {
  mode: 'standard',
  source: 'remote',
}
```

不推荐：

```ts
featureMode: 'standard'
featureSource: 'remote'
```

### 3.4 使用者体验

- 最常见用法必须最短、最直观、最不容易错。
- 使用者代码只表达业务意图，不暴露内部 key、内部路径、内部协议字符串或重复样板。
- 多个使用点重复的配置，应收敛成所属功能自己的导出，不让全局层重复拼装。
- 复杂功能的内部组合应就近放在功能目录，不散落到全局入口或基础模块。
- 默认行为不能偷偷污染复杂业务场景；可选入口、附加能力和扩展点必须显式启用。
- 如果使用者必须阅读内部源码才能正确调用，说明 API 还不够好。

## 4. 命名规则

### 4.1 总体原则

- 命名表达领域语义，不表达实现偶然性。
- 先命名职责，再命名实现，不用技术形态掩盖领域含义。
- 命名短而准：上下文已经表达的领域词不要重复写进函数名、字段名或文件名。
- 短名只能在上下文足够明确时使用；脱离上下文会含糊时必须补足对象或目标。
- 文件名、导出名和类型名必须匹配职责，不用过宽泛名字掩盖多职责。
- 公开命名一旦发布就视为契约；改名时旧名必须同轮删除并做残留扫描。

### 4.2 对象与字段命名

- 嵌套对象内不要重复父级语义；例如在 `user` 下写 `id/name`，不要写 `userId/userName`。
- 字段名避免泛泛的 `state`、`data`、`value`、`info`、`item`，除非它们就是领域术语。
- 不用 `common`、`helper`、`utils`、`manager` 这类宽泛名字承载多职责。
- 集合和单项要区分清楚：集合名表达复数或集合语义，单项名表达具体实体语义。
- 两态字段使用肯定语义布尔名，例如 `visible`、`enabled`、`open`。
- 超过两态时使用 `mode`、`status`、`phase` 等枚举字段，不继续堆 boolean。
- 枚举值必须属于同一维度，不把来源、状态、权限、展示方式混在一个枚举里。

推荐：

```ts
user: { id, name }
status: 'idle' | 'loading' | 'success' | 'error'
```

不推荐：

```ts
user: { userId, userName, data }
loading + loaded + failed
```

### 4.3 动作与类型命名

- 动作命名要区分读取、创建、更新、删除、重置、同步、解析、归一化、校验。
- 纯转换函数用结果语义命名，副作用函数用动作语义命名。
- adapter 命名必须包含被适配对象或目标环境。
- 位于模块内部时，类型和函数名不需要反复写模块名。
- 位于 `types/internal.ts`、`runtime/`、`components/` 等内部目录时，命名不需要再写 `Internal`。
- 长名只有在跨模块、跨领域或脱离上下文会含糊时才成立。

推荐：

```ts
type RenderContext = {}
type ResolvedEntry = {}
function showEntry() {}
function cacheKey() {}
function syncRemote(adapter) {}
```

不推荐：

```ts
type ModuleRenderContext = {}
type ResolvedModuleEntry = {}
function shouldRenderModuleEntry() {}
function resolveModuleRouteCacheKey() {}
function sync(adapter) {}
```

### 4.4 约定字符串

- 外部 key 遵循对应生态和协议的命名习惯。
- 内部对象命名遵循当前语言约定，并保持短语义。
- 约定字符串必须集中定义或由 helper 生成，不散落在业务使用点。
- 使用者不应手写内部协议字符串；如果必须手写，说明缺少公共 helper 或配置入口。

## 5. 对象、状态与数据

### 5.1 对象设计

- 对象先按领域分组，再按职责分层。
- 对象字段表达“是什么”，方法表达“做什么”。
- 对象内部字段不要重复对象名已经表达的语义。
- 对象层级不宜过深；超过三层仍频繁访问时，应考虑拆成子对象或 helper。
- 同一对象内字段必须处于同一抽象层级。
- 不要把原始输入、派生值、展示文案和副作用控制混在一起。
- 对象可以承载配置、状态、上下文或结果，但不要同时承担多种角色。
- 结果对象应明确成功、失败和附加信息，不用松散字段让调用方猜。

推荐：

```ts
session: { id, user, runtime }
```

不推荐：

```ts
session: { sessionId, userId, displayText, onRetry }
```

### 5.2 状态设计

- 一个状态只能有一个真实来源，其它值必须派生。
- 不同时保存会互相推导或互相冲突的多个 boolean。
- 多状态组合优先使用枚举，避免非法组合。
- 用户偏好、运行态和业务数据分层管理。
- `preferences` 表示用户选择和可持久化配置。
- `runtime` / `ui` 表示打开态、折叠态、选中临时对象、请求中等运行态，默认不持久化。
- `data` 表示业务数据或领域数据。
- 模块只能写自己契约内的状态。
- 需要影响宿主业务时，通过 adapter、事件或显式 action 交给宿主实现。
- 状态转换要集中，不能散落在多个调用点里互相覆盖。
- 异步状态必须定义开始、成功、失败、取消或过期时的行为。

### 5.3 多来源数据

- 同一结果由多个来源组成时，必须定义来源、顺序、去重键和操作权限。
- 内置项、用户项、远程项、运行时项等来源共存时，必须先归一化再合并。
- 去重键必须使用稳定业务标识，不能使用会随上下文抖动的展示值。
- 可执行、可删除、可更新、可固定等操作权限应由数据项语义决定。
- 数据来源可以由 adapter 提供；基础模块不得直接依赖宿主状态实现。
- 合并后的数据结构必须稳定，避免每个使用点自己再做不同解释。

### 5.4 调用单元与上下文

- 复杂函数、组件或模块优先接收对象化上下文，不接收散开的状态和动作。
- 同一能力的不同接入方式必须共用同一调用契约。
- 输入向内传递，结果通过返回值、事件或显式回调向外表达。
- 跨深层结构的共享能力才使用上下文；简单父子或单层调用不需要强行 context 化。
- 调用单元需要知道场景或能力时，优先使用显式上下文字段，不手动解析内部字符串。
- 入口层保持薄入口，只组合模块，不承载完整业务实现。
- 业务功能细节收敛在功能目录内，不散落到全局入口或基础模块。

## 6. 扩展、错误与副作用

### 6.1 扩展点

- 扩展点必须有统一契约和固定优先级。
- 默认能力、注册表、配置对象、显式覆盖、回调或钩子等多来源共存时，必须写清楚合并顺序。
- 整体覆盖优先于局部组合；整体交给使用者后，不再混入默认局部内容。
- 可选能力应作为普通可组合扩展，不在核心逻辑里硬编码特殊字段。
- 注册表适合复用一组能力。
- 内联配置适合少量本地强绑定。
- adapter 适合外部能力接入。
- 回调或钩子适合特殊兜底。
- 不要为了单个业务场景污染通用扩展机制。
- 扩展点的输入输出必须稳定，不能让扩展实现依赖内部临时结构。

### 6.2 错误与副作用

- 模块边界处必须明确错误如何表达：抛出、返回结果对象、事件通知或交给 adapter。
- 不要吞掉错误；无法处理的错误要向调用方暴露足够上下文。
- 副作用必须集中在明确入口，例如初始化、提交、保存、同步、销毁。
- 初始化和清理必须成对设计，避免残留监听、缓存、定时器或注册项。
- 网络、存储、计时器、全局对象等外部资源应通过 adapter 或封装层访问，便于测试和替换。
- 可取消、可重试、可并发的动作必须定义冲突处理规则。

### 6.3 旧入口删除

- 生成或修改代码时优先删除错误抽象，不保留会诱导继续错误使用的旧字段。
- 同一能力只保留当前推荐入口，不同时支持新旧两套契约。
- 旧 API、旧类型、旧变量名、旧文件名、旧 demo 文案和旧文档标题必须同轮删除。
- 不为旧名字保留别名，不新增旧契约目录，不让核心逻辑同时支持新旧两套契约。
- 删除旧入口前必须明确替代入口、影响范围和验证方式。
- 删除旧入口后必须按实际旧名扫描代码、文档、demo、注释和类型说明。
- 发现平行字段、临时开关、绕过主入口的特殊参数或特殊回调时，先重新审视边界，而不是继续扩展补丁。

残留扫描至少覆盖：

```txt
旧 API 名
旧类型名
旧变量名
旧文件名
旧 demo 文案
旧 README 示例
旧设计说明标题
旧注释中的推荐写法
```

## 7. 注释、文档与 demo

### 7.1 注释规则

注释应说明用途、契约、设计原因和保护点，不复述代码字面意思。

必须注释：

- 公开 API、公开类型、公开配置和公开 adapter。
- 非显而易见的约束、默认值、优先级、状态转换和失败保护。
- 关键处理逻辑的设计要求：为什么按这个顺序处理、为什么不能合并、为什么不能提前返回。
- 会产生副作用、缓存、异步、重试、取消、并发或资源占用的入口。
- 错误表达方式：会抛出、会返回错误对象，还是交给 adapter。
- 不变量和边界条件：调用前提、调用后保证、不能做什么。
- 容易在修改中被误删的逻辑保护点，例如去重、排序、兜底、清理和资源释放。

不要注释：

- 代码字面意思，例如“设置变量”“遍历数组”“返回结果”。
- 已经能由好命名表达的内容。
- 临时解释、情绪化说明、历史流水账和没有维护价值的背景故事。
- 与实现不一致的愿望式说明。

推荐：

```ts
/** 获取当前配置。除非 force 为 true，否则返回缓存值；刷新失败时抛出错误。 */
```

```ts
// 先归一化再合并，保证本地项和远程项使用同一去重键；不要把两个步骤合并。
```

不推荐：

```ts
/** 获取数据 */
```

### 7.2 注释位置

- 公共出口写使用契约。
- adapter 写外部系统差异和失败语义。
- 内部复杂逻辑写设计原因、处理顺序、不变量和失败保护。
- 关键代码块写设计要求和保护点，避免修改时只看局部实现而删掉必要逻辑。
- 旧入口删除范围、规则和边界约束写入文档，不只留在聊天记录里。

### 7.3 文档与 demo

- 详细设计文档可以写推理过程；规则文档必须短、硬、可执行。
- 可执行文档必须包含推荐写法、不推荐写法、优先级、删除项或 Review 检查项。
- API、命名、状态结构或接入方式变化时，同步更新 README、设计说明、公共类型注释、demo 文案和真实用法。
- README 必须描述公共用法、边界、扩展方式、旧入口删除规则和验证方式。
- 文档示例必须使用最新公共入口，不保留“能运行但不推荐”的旧写法。
- demo 必须用真实入口、真实组件、真实配置或真实 adapter 展示能力，不能只写文字说明。
- 设计说明里的伪代码如果引用函数名、类型名或公共入口，也按源码同等标准维护。
- 文档过期等同于实现不完整。

## 8. 验证规则

- 默认路径必须有验证。
- 至少一个扩展路径必须有验证。
- 状态转换、错误路径和清理逻辑必须有验证。
- 文档声称的公共 API 必须能通过类型检查或最小调用示例证明。
- 对纯逻辑模块，优先使用单元测试验证输入输出和边界条件。
- 对集成模块，至少验证依赖注入、adapter 调用和失败回退。
- 修改公共契约时，要验证真实调用方、demo 和文档示例。
- 没有自动化测试条件时，必须记录手动验证命令、观察点和未验证项。

验证结论必须明确：

```txt
已验证：默认路径、扩展路径、错误路径。
未验证：浏览器交互。原因：未启动 dev server。
风险：样式断点需要后续人工检查。
```

## 9. 一行函数去留

- 只做转发、只用一次、名字还比调用本身更长的一行函数应删除或内联。
- 类型守卫、公共工具、边界转换、模板复用和隐藏内部字符串的一行函数可以保留。
- 保留一行函数时必须能说清它提供的语义边界；说不清就是噪音。

可以保留：

```ts
function toList(input: unknown): Record[]
function hasItems(config: ResolvedEntry): boolean
```

应该删除或改短：

```ts
function shouldOverride(input, overrideName) {
  return Boolean(overrideName && !input)
}

function isCurrentPath(path) {
  return activePath.value === path
}
```

## 10. 变更准入检查

“变更准入检查”指修改进入实现前必须满足的设计与质量检查，不是权限控制。

修改长期维护模块、内部库、公共组件、公共类型、公共配置或演示模块前，必须确认：

- **职责清楚**：模块职责和非职责已经说明。
- **入口简单**：公共入口少、稳定、好记，默认路径短。
- **边界明确**：输入、输出、状态所有权和副作用边界清楚。
- **依赖正确**：基础模块没有直接依赖具体业务实现。
- **命名短准**：变量、函数、类型、文件名不重复父级语义。
- **规则唯一**：同一规则只有一个实现入口，没有多处近似逻辑漂移。
- **配置优先**：配置、注册表、预设或 adapter 能表达的能力，没有新增函数式 DSL。
- **helper 有意义**：helper 只消除内部字符串、重复结构或易错样板，不制造第二套配置语言。
- **状态唯一**：状态只有一个真实来源，派生值不重复保存。
- **扩展稳定**：扩展点契约、合并顺序和优先级清楚。
- **旧入口删净**：旧 API、旧文档、旧 demo、旧注释、旧类型名同轮删除。
- **注释有效**：保留说明优先级、边界、状态来源和安全约束的注释；删除复述代码字面意思的注释。
- **demo 真实**：demo 使用真实入口、真实组件、真实配置或真实 adapter。
- **文档同步**：README、规则文档、类型注释、demo 文案和真实用法一致。
- **验证闭环**：默认路径、至少一个扩展路径和错误路径已验证。

改动完成后，按实际旧名扫描代码、文档、demo 和注释。扫描没有结果，才算旧模式真正删干净。

## 11. Review 检查清单

- [ ] 模块职责和非职责是否清楚？
- [ ] 是否直接依赖了不该依赖的业务实现？
- [ ] 公共入口是否对象化，而不是暴露零散参数或零散回调？
- [ ] 公开输入、输出、错误和事件契约是否明确？
- [ ] 使用者是否需要知道内部 key、内部路径或重复样板？
- [ ] 重复配置是否已经收敛为功能级导出？
- [ ] 命名是否重复父级语义或含糊表达状态？
- [ ] 公共 API 名称是否面向使用者意图，而不是暴露内部实现形态？
- [ ] 是否存在 `data`、`info`、`item`、`helper`、`manager` 等掩盖职责的泛名？
- [ ] 动作命名是否能区分读取、转换、写入、副作用和外部适配？
- [ ] 对象字段是否按领域和职责分组，而不是混合多种抽象层级？
- [ ] 对象是否同时承担配置、状态、上下文、结果等多种角色？
- [ ] 状态是否只有一个真实来源？
- [ ] 多状态组合是否应该改成枚举？
- [ ] 用户偏好、运行态、业务数据是否分层？
- [ ] 多来源数据是否定义了来源顺序、去重键和操作权限？
- [ ] 扩展点契约和优先级是否清楚？
- [ ] 复杂功能的细节是否收敛在功能目录？
- [ ] 目录是否区分公共出口、核心逻辑、适配层和运行态？
- [ ] 是否生成了没有实际用途的空目录或空架子？
- [ ] 错误、副作用和清理逻辑是否有明确边界？
- [ ] 公开 API 注释是否先说明功能，再说明契约？
- [ ] 关键代码块是否写明设计要求和不能丢失的保护点？
- [ ] 复杂逻辑注释是否说明原因、处理顺序、不变量和边界条件？
- [ ] 删除旧字段或旧入口时，替代入口、影响范围和验证方式是否明确？
- [ ] 旧 API 是否已经从代码、文档、demo、注释和类型说明中全部删除？
- [ ] 是否没有为了“稳妥”保留会诱导继续错误使用的旧别名？
- [ ] 是否没有新增旧契约目录、旧入口分支或影子路径？
- [ ] 核心逻辑是否只支持当前推荐契约，没有同时分叉支持新旧两套入口？
- [ ] 是否新增了零散参数、零散回调或平行字段？
- [ ] 是否新增了补丁式字段而不是修正设计入口？
- [ ] README、规则文档、类型注释、demo 文案和真实用法是否一致？
- [ ] demo 是否用真实入口、真实组件、真实配置或真实 adapter 展示能力？
- [ ] 是否对旧 API、旧类型名、旧变量名、旧文件名、旧 demo 文案做了残留扫描？
- [ ] 涉及模块契约时，是否检查了整个模块目录而不是只改当前报错文件？
- [ ] 默认路径、扩展路径和错误路径是否都已验证？
