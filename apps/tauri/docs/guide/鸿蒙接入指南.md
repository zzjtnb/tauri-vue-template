# Tauri OpenHarmony / HarmonyOS 标准接入指南

本文定义本项目接入 OpenHarmony / HarmonyOS 的唯一标准路径。所有鸿蒙工程、Rust 依赖、Tauri 配置、权限、签名和构建命令均围绕现有 `src-tauri/` 维护。

## 命令怎么写

脚本在 `apps/tauri/package.json`。任选一种方式，**与 Android / iOS 相同**（鸿蒙没有额外前缀规则）：

| | 写法 |
| --- | --- |
| **方式 A**（在 `apps/tauri` 内） | `cd apps/tauri` 后执行 `pnpm harmony:build` |
| **方式 B**（在仓库根） | `pnpm --dir apps/tauri harmony:build` |

下文步骤若只写 `pnpm harmony:*`，默认指**方式 A**；在根目录请改成方式 B。

标准构建命令：

```bash
# 方式 A
cd apps/tauri && pnpm harmony:build

# 方式 B（仓库根）
pnpm --dir apps/tauri harmony:build
```

配置签名材料后的标准签名产物：

```text
src-tauri/gen/ohos/entry/build/default/outputs/default/entry-default-signed.hap
```

公开模板不提交 OpenHarmony 签名材料；未配置签名材料时，构建可能生成 unsigned HAP 或在签名阶段提示缺少 signing config。

## 核心原则

1. **鸿蒙接入使用现有 `src-tauri/` 工程**。
   - 鸿蒙原生工程由 Tauri OHOS CLI 生成。
   - 生成目录固定为 `src-tauri/gen/ohos/`。
2. **鸿蒙命令使用 OpenHarmony 分支的 Tauri CLI 和依赖**。
   - `cargo tauri ohos ...` 是鸿蒙初始化、开发和构建入口。
   - `Cargo.toml` 使用 `tauri-apps/tauri` 的 `feat/open-harmony` 分支。
3. **插件和 capability 按平台隔离**。
   - 非 OHOS 插件通过 `target_env = "ohos"` 排除。
   - OpenHarmony 使用单独的 `ohos` capability。
4. **签名配置使用 Hvigor 可解密的成套材料**。
   - `storePassword` / `keyPassword` 使用 DevEco/Hvigor 加密值。
   - 加密值与 `signature/material/fd`、`signature/material/ac`、`signature/material/ce` 成套维护。

## 快速开始

首次接入或新机器恢复时，按以下顺序完成最短路径验证：

1. 安装 OpenHarmony 版 Tauri CLI。
2. 执行 `cargo tauri ohos -h`，确认存在 `init`、`dev`、`build`。
3. 确认 `package.json` 中存在 `harmony:*` 脚本。
4. 确认 `src-tauri/Cargo.toml` 使用 `feat/open-harmony` 分支依赖。
5. 执行 `pnpm harmony:init`（在 `apps/tauri` 内；仓库根见上文方式 B）生成 `src-tauri/gen/ohos/`。
6. 确认 `entry/oh-package.json5`、`EntryAbility.ets`、`build-profile.json5` 与本文标准配置一致。
7. 按需生成本机私有 `src-tauri/gen/ohos/signature/` 签名材料。
8. 执行 `pnpm harmony:build`（方式 A；仓库根为 `pnpm --dir apps/tauri harmony:build`）。
9. 未配置签名时验收 unsigned HAP；配置签名后验收 `entry-default-signed.hap`。

快速验收命令：

```bash
cargo tauri ohos -h
pnpm harmony:build                    # 方式 A（在 apps/tauri 内）
pnpm --dir apps/tauri harmony:build   # 方式 B（仓库根）
```

快速验收产物：

```text
src-tauri/gen/ohos/entry/build/default/outputs/default/entry-default-unsigned.hap
```

配置签名材料后，验收产物为：

```text
src-tauri/gen/ohos/entry/build/default/outputs/default/entry-default-signed.hap
```

## 2. 环境要求

本地环境包含以下工具：

- Node.js：满足 `package.json` 的 `engines`。
- pnpm：项目脚本统一使用 pnpm。
- Rust：满足 `src-tauri/Cargo.toml` 的 `rust-version`。
- DevEco Studio / OpenHarmony SDK：提供 `hvigor`、`ohpm`、toolchains 和签名工具。
- OpenHarmony 版 Tauri CLI：提供 `cargo tauri ohos`。
- `ohrs`：OpenHarmony Rust 构建辅助工具。

安装 OpenHarmony 版 Tauri CLI：

```bash
cargo install tauri-cli --git https://github.com/tauri-apps/tauri --branch feat/open-harmony
```

检查命令：

```bash
cargo tauri ohos -h
```

标准输出包含 `init`、`dev`、`build` 子命令。

### 版本矩阵

当前项目按以下版本和分支组合维护：

| 项 | 标准值 |
| --- | --- |
| Tauri Rust crates | `https://github.com/tauri-apps/tauri` / `feat/open-harmony` |
| Tauri JS packages | 与当前 Rust crates 实际解析版本保持同步 |
| Tauri OHOS CLI | `cargo tauri ohos` |
| OHOS build target | `--target aarch64` |
| OpenHarmony SDK | `5.0.0(12)` |
| ArkTS ability 包 | `@ohos-rs/ability@0.4.0-beta.7` |
| Rust OHOS NAPI | `napi-ohos = "1.1"`、`napi-derive-ohos = "1.1"` |
| 主要验收产物 | `entry-default-signed.hap`；release 归档扫描同时识别 OpenHarmony `.app`、`.hap`、`.har` |

版本策略：Tauri 官方要求 JS 侧 npm 包与 Rust 侧 Cargo crate 保持兼容版本。当前项目保留 `feat/open-harmony` 分支时，Rust 侧版本由该分支实际解析结果决定；JS 侧 `@tauri-apps/api` 需要与 `tauri` crate 保持同 minor，插件包需要与对应 Rust 插件 crate 精确对齐。不要在标准脚本中使用 `--ignore-version-mismatches` 绕过真实版本不一致。

版本升级时按这个顺序验证：

1. `git ls-remote https://github.com/tauri-apps/tauri feat/open-harmony`，确认 OpenHarmony 分支最新提交。
2. `cargo tauri ohos -h`。
3. 按 Tauri 配置执行默认示例应用前端构建。
4. `pnpm --dir apps/tauri harmony:build`。
5. `src-tauri/gen/ohos/entry/build/default/outputs/default/entry-default-signed.hap` 存在。

## 5. Rust 运行时代码

`src-tauri/src/lib.rs` 以 `target_env = "ohos"` 为平台边界。OHOS 运行时使用 Tauri core 和命令能力；其他平台继续注册项目插件。

标准结构：

```rust
mod commands;
mod services;
mod state;

use commands::*;
use services::*;
use state::AppState;

// Learn more about Tauri commands at https://tauri.app/develop/calling-rust/
#[tauri::command]
fn greet(name: &str) -> String {
    format!("你好，{}！这条消息来自 Rust。", name)
}

#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() {
    let builder = tauri::Builder::default().manage(AppState::default());

    #[cfg(not(target_env = "ohos"))]
    let builder = builder
        .plugin(tauri_plugin_upload::init())
        .plugin(tauri_plugin_os::init())
        .plugin(tauri_plugin_fs::init())
        .plugin(tauri_plugin_opener::init());

    builder
        .invoke_handler(tauri::generate_handler![greet, opened_urls])
        .setup(|_app| {
            #[cfg(desktop)]
            {
                _app.handle()
                    .plugin(tauri_plugin_window_state::Builder::new().build())?;
                _app.handle()
                    .plugin(tauri_plugin_updater::Builder::new().build())?;
                _app.handle()
                    .plugin(tauri_plugin_autostart::Builder::new().build())?;
            }

            #[cfg(all(debug_assertions, not(target_env = "ohos")))]
            {
                _app.handle().plugin(
                    tauri_plugin_log::Builder::default()
                        .level(log::LevelFilter::Info)
                        .build(),
                )?;
            }

            Ok(())
        })
        .build(tauri::generate_context!())
        .expect("error while building tauri application")
        .run(handle_run_event);
}
```

`src-tauri/src/state/app_state.rs` 中与打开 URL 事件相关的写入能力绑定到支持该事件的平台：

```rust
#[cfg(any(target_os = "macos", target_os = "ios", target_os = "android"))]
pub(crate) fn extend_opened_urls(&self, urls: Vec<tauri::Url>) {
    self.opened_urls.lock().unwrap().extend(urls);
}
```

## 8. 生成 OHOS 工程

执行初始化：

```bash
pnpm --dir apps/tauri harmony:init
```

初始化后确认目录存在：

```text
src-tauri/gen/ohos/
├── AppScope/
├── assets/
├── entry/
├── hvigor/
├── build-profile.json5
├── hvigorfile.ts
└── oh-package.json5
```

接入后需要维护的生成文件：

```text
src-tauri/gen/ohos/build-profile.json5
src-tauri/gen/ohos/entry/oh-package.json5
src-tauri/gen/ohos/entry/src/main/ets/entryability/EntryAbility.ets
src-tauri/gen/ohos/signature/
```

重新初始化或同步生成目录时，以上文件是项目契约的一部分。`build-profile.json5` 保存 SDK、product、签名和 module 关系；`entry/oh-package.json5` 保存 ArkTS 侧依赖；`EntryAbility.ets` 保存 Rust 动态库加载入口；`signature/` 保存 HAP 签名材料。

### 重建与迁移规则

新机器恢复、删除生成目录、升级 DevEco SDK 或重新执行 `pnpm --dir apps/tauri harmony:init` 后，按以下规则恢复：

| 场景 | 处理方式 | 验收 |
| --- | --- | --- |
| 新机器首次拉取项目 | 安装 OpenHarmony 版 Tauri CLI、DevEco SDK、Rust 工具链和 pnpm 依赖 | `cargo tauri ohos -h` 可用 |
| 重新生成 `src-tauri/gen/ohos/` | 重新核对 `build-profile.json5`、`entry/oh-package.json5`、`EntryAbility.ets`、`signature/` | `pnpm --dir apps/tauri harmony:build` 成功 |
| 删除 `oh_modules` | 由 `pnpm --dir apps/tauri harmony:build` 触发 OHPM 重新安装 | `entry/oh_modules/@ohos-rs/ability` 可解析 |
| 更换签名材料 | 替换 `signature/` 并同步 `build-profile.json5` 签名字段 | 产物为 `entry-default-signed.hap` |
| 升级 `@ohos-rs/ability` | 同步检查导出的 Ability 基类和 ArkTS warning | `CompileArkTS` 成功 |

稳定源码入口是 `src-tauri/`、`src-tauri/gen/ohos/entry/`、`src-tauri/gen/ohos/signature/`。`oh_modules` 是 OHPM 安装产物，只作为构建缓存处理。

## 10. EntryAbility 标准实现

`src-tauri/gen/ohos/entry/src/main/ets/entryability/EntryAbility.ets` 使用 `NativeAbility`，动态库名为 `app_lib`，渲染模式为 `webview`：

```ts
import { NativeAbility } from '@ohos-rs/ability'
import Want from '@ohos.app.ability.Want'
import { AbilityConstant } from '@kit.AbilityKit';
import window from '@ohos.window';

export default class EntryAbility extends NativeAbility {
  public moduleName: string = "app_lib"
  public defaultPage: boolean = true;
  public mode: 'xcomponent' | 'webview' = 'webview'

  async onCreate(want: Want, launchParam: AbilityConstant.LaunchParam): Promise<void> {
    try {
      super.onCreate(want, launchParam);
    }
    catch (error) {
      console.error('EntryAbility onCreate failed:', error);
    }
  }

  async onWindowStageCreate(windowStage: window.WindowStage): Promise<void> {
    try {
      const window = windowStage.getMainWindowSync();
      await window.setWindowLayoutFullScreen(false);
      super.onWindowStageCreate(windowStage);
    }
    catch (error) {
      console.error('EntryAbility onWindowStageCreate failed:', error);
    }
  }
}
```

字段约定：

- `moduleName`：Rust 动态库名，对应 `Cargo.toml` 的 `[lib].name = "app_lib"`。
- `defaultPage`：启用默认页面加载。
- `mode`：使用 `webview`。
- `onCreate` / `onWindowStageCreate`：用 `try/catch` 包裹 OpenHarmony 可能抛异常的生命周期调用。

## 11. build-profile.json5 标准配置

`src-tauri/gen/ohos/build-profile.json5` 同时声明 SDK、product、module 和可选签名配置。公开模板默认不提交签名材料，因此实际文件中的 `signingConfigs` 为空；开发者生成私有签名材料后，再按下面结构补齐签名配置。

```json5
{
  "app": {
    "signingConfigs": [
      {
        "name": "default",
        "material": {
          "storeFile": "signature/OpenHarmony.p12",
          "storePassword": "<DevEco/Hvigor 加密值>",
          "keyAlias": "OpenHarmony Application Release",
          "keyPassword": "<DevEco/Hvigor 加密值>",
          "signAlg": "SHA256withECDSA",
          "profile": "signature/examples-profile.p7b",
          "certpath": "signature/OpenHarmonyApplication.pem"
        }
      }
    ],
    "products": [
      {
        "name": "default",
        "signingConfig": "default",
        "compatibleSdkVersion": "5.0.0(12)",
        "targetSdkVersion": "5.0.0(12)",
        "runtimeOS": "HarmonyOS",
        "buildOption": {
          "strictMode": {
            "caseSensitiveCheck": true,
            "useNormalizedOHMUrl": true
          }
        }
      }
    ],
    "buildModeSet": [
      {
        "name": "debug",
      },
      {
        "name": "release"
      }
    ]
  },
  "modules": [
    {
      "name": "entry",
      "srcPath": "./entry",
      "targets": [
        {
          "name": "default",
          "applyToProducts": ["default"]
        }
      ]
    }
  ]
}
```

`targetSdkVersion` 和 `compatibleSdkVersion` 当前统一使用：

```text
5.0.0(12)
```

## 12. 签名材料

签名材料的项目目录为：

```text
src-tauri/gen/ohos/signature/
```

公开模板不提交实际签名材料。目录中只保留说明文件；本地开发、测试安装或正式发布时，由开发者通过 DevEco Studio / Hvigor 生成并私有注入以下文件结构：

```text
src-tauri/gen/ohos/signature/
├── OpenHarmony.p12
├── OpenHarmonyApplication.cer
├── OpenHarmonyApplication.pem
├── examples-profile.json
├── examples-profile.p7b
└── material/
    ├── ac/material
    ├── ce/material
    └── fd/*/material
```

字段对应关系：

| build-profile 字段 | 文件或值 |
| --- | --- |
| `storeFile` | `signature/OpenHarmony.p12` |
| `storePassword` | Hvigor 加密后的 keystore 密码 |
| `keyAlias` | `OpenHarmony Application Release` |
| `keyPassword` | Hvigor 加密后的 key 密码 |
| `signAlg` | `SHA256withECDSA` |
| `profile` | `signature/examples-profile.p7b` |
| `certpath` | `signature/OpenHarmonyApplication.pem` |

`storePassword` / `keyPassword` 与 `signature/material/` 成套使用。迁移签名材料时，这三个部分作为一个整体维护：

```text
OpenHarmony.p12
build-profile.json5 中的加密密码
signature/material/
```

正式发布流程必须使用团队正式证书、profile、keystore 和 DevEco/Hvigor 生成的签名材料。

### 测试签名与正式发布边界

公开模板不内置 OpenHarmony 签名材料，边界如下：

| 用途 | 使用材料 | 验收 |
| --- | --- | --- |
| 本地开发构建 | 开发者本机生成的测试 `signature/` | `entry-default-signed.hap` |
| 测试安装验证 | 本机测试证书或团队测试证书 | 目标设备可安装运行 |
| 团队正式发布 | 团队正式 keystore、profile、证书链、Hvigor material | 发布渠道签名校验通过 |

正式发布替换签名材料时保持构建流程不变，只替换以下输入：

```text
signature/OpenHarmony.p12
signature/OpenHarmonyApplication.pem
signature/examples-profile.p7b
signature/material/
build-profile.json5 中的 signingConfigs.material
```

签名材料替换后，`products[].signingConfig` 仍指向实际存在的 `signingConfigs[].name`。

### 签名材料来源

本地开发签名材料可由 OpenHarmony SDK 的公开测试材料派生，并转换成 Hvigor 可读取的项目内签名目录。涉及的 SDK 文件通常位于 DevEco Studio 安装目录的 OpenHarmony toolchains 下：

```text
OpenHarmony.p12
OpenHarmonyProfileRelease.pem
UnsgnedReleasedProfileTemplate.json
hap-sign-tool.jar
```

项目内 `signature/` 是构建真正读取的来源，但公开模板不会提交真实材料。迁移或重建环境时，以本机私有生成后的项目内目录为准：

```text
src-tauri/gen/ohos/signature/
```

团队正式发布时，用正式签名材料替换同一目录结构，并同步更新 `build-profile.json5` 中的 `storeFile`、`storePassword`、`keyAlias`、`keyPassword`、`profile`、`certpath`。

### 签名替换验收

替换签名材料后执行：

```bash
pnpm --dir apps/tauri harmony:build
```

验收项：

1. `SignHap` 阶段成功。
2. 产物文件名包含 `signed`。
3. 输出路径为 `entry-default-signed.hap`。
4. `build-profile.json5` 中 `products[].signingConfig` 指向实际存在的 `signingConfigs[].name`。

## 13. 构建流程

执行：

```bash
pnpm --dir apps/tauri harmony:build
```

构建阶段顺序：

1. Tauri 按配置执行示例应用的前端构建命令。
2. Cargo：Rust 编译为 OHOS native library。
3. OHPM：安装 `entry/oh-package.json5` 依赖。
4. Hvigor：编译 ArkTS、资源和 HAP。
5. SignHap：签名 HAP。

成功日志包含：

```text
BUILD SUCCESSFUL
Finished 1 HAP at:
  src-tauri/gen/ohos/entry/build/default/outputs/default/entry-default-signed.hap
```

验收标准：

```text
src-tauri/gen/ohos/entry/build/default/outputs/default/entry-default-signed.hap
```

## 14. 构建阶段定位

按日志阶段定位问题：

| 阶段 | 关注点 |
| --- | --- |
| 前端构建命令 | TypeScript、Vite、CSS、UnoCSS |
| Cargo | Rust 依赖、target cfg、Tauri patch |
| OHPM | `entry/oh-package.json5` 依赖版本 |
| CompileArkTS | `EntryAbility.ets`、`@ohos-rs/ability`、ArkTS API |
| SignHap | `build-profile.json5`、`signature/`、证书链、加密密码 |

签名阶段日志和配置对应关系：

| 日志特征 | 对应配置 |
| --- | --- |
| `No signingConfigs profile` | `app.signingConfigs` 和 `products[].signingConfig` |
| `storePassword or keyPassword` | `material.storePassword` / `material.keyPassword` |
| `signature/material` | `storeFile` 同级 `material/` 目录 |
| `cert chain` | `material.certpath` 指向完整证书链 |

## 15. 常见问题

本章保留接入过程中出现过的反例和疑难杂症。标准流程仍以前文为准；本章用于看到相同日志或配置时快速定位。

### 15.1 `cargo tauri ohos` 不存在

现象：

```text
error: unrecognized subcommand 'ohos'
```

原因：当前命中的 Tauri CLI 不是 OpenHarmony 分支版本。

处理：安装并使用 OpenHarmony 分支 CLI：

```bash
cargo install tauri-cli --git https://github.com/tauri-apps/tauri --branch feat/open-harmony
cargo tauri ohos -h
```

验收：帮助信息中出现 `init`、`dev`、`build`。

### 15.2 Cargo.toml 指向本地路径

反例：

```toml
tauri-build = { path = "../backup/tauri/crates/tauri-build", features = [] }
tauri = { path = "../backup/tauri/crates/tauri", features = [] }
```

原因：本地路径依赖会把项目绑定到个人机器上的临时目录，其他环境无法复现。

处理：统一使用 OpenHarmony 分支 git 依赖：

```toml
tauri-build = { git = "https://github.com/tauri-apps/tauri", branch = "feat/open-harmony", features = [] }
tauri = { git = "https://github.com/tauri-apps/tauri", branch = "feat/open-harmony", features = [] }
```

验收：`Cargo.toml` 中 Tauri 相关依赖不包含本地 `path`。

### 15.3 出现独立鸿蒙工程目录

反例：

```text
src-tauri-harmony/
```

原因：鸿蒙工程脱离现有 `src-tauri/` 后，会产生第二套 Tauri 配置、Rust 依赖、capability 和签名材料，后续维护会分叉。

处理：鸿蒙工程由 `pnpm --dir apps/tauri harmony:init` 生成到：

```text
src-tauri/gen/ohos/
```

验收：鸿蒙相关原生工程只在 `src-tauri/gen/ohos/` 下维护。

### 15.4 tauri.conf.json 解析 Android 字段失败

现象：

```text
Additional properties are not allowed ('debugApplicationIdSuffix' was unexpected)
```

原因：OpenHarmony 分支 CLI 使用的 Tauri schema 不一定识别较新的 Android 专用字段。即使字段放在 `src-tauri/tauri.conf.json` 的 `bundle.android`，也会被移动端构建链读取并校验。

处理：当前模板的 `src-tauri/tauri.conf.json` 的 `bundle.android` 只保留 `minSdkVersion` 和 `versionCode` 这类当前 schema 支持的字段；需要新增 Android 专用字段时，先确认当前 Tauri CLI / `tauri-build` schema 支持，再写入配置。

验收：`cargo tauri ohos init/build` 和 `pnpm android:build` 都能正常解析 Tauri 配置。

### 15.5 `tauri info` 提示 Tauri 版本不一致

现象：

```text
Found version mismatched Tauri packages
```

原因：JS 侧 Tauri npm 包与 Rust 侧 Cargo crate 未按官方兼容规则同步。当前项目保留 `feat/open-harmony` 分支时，Rust 侧实际版本由该分支决定；如果 JS 侧使用更新的 npm 版本，就会出现版本不一致提示。

处理：以当前 Rust 侧实际解析版本为基准同步 JS 侧 Tauri 包。`@tauri-apps/api` 与 `tauri` crate 保持同 minor；插件 npm 包与对应 Rust 插件 crate 精确对齐；标准脚本不使用 `--ignore-version-mismatches`。

```bash
pnpm --dir apps/tauri harmony:build
```

验收：`pnpm --dir apps/tauri harmony:build` 生成 signed HAP；如出现真实 API 或构建错误，先核对 JS/Rust Tauri 版本矩阵，再按错误栈定位。

### 15.6 capability permission 不存在

现象：

```text
Permission opener:default not found
```

原因：OHOS 下未注册 `opener`、`fs`、`os`、`upload` 等插件 permission，但 capability 仍引用了这些权限。

处理：桌面、Android、iOS 使用 `default` capability；OpenHarmony 使用 `ohos` capability，权限保持：

```json
["core:default"]
```

验收：`src-tauri/capabilities/ohos.json` 只声明 OpenHarmony 可用的最小权限。

### 15.7 TypeScript 6 报 baseUrl 弃用

现象：

```text
TS5101: Option 'baseUrl' is deprecated and will stop functioning in TypeScript 7.0.
```

原因：TypeScript 6 对 `baseUrl` 给出弃用诊断。

处理：根 `tsconfig.json` 删除 `baseUrl`，保留项目路径别名：

```json
{
  "compilerOptions": {
    "paths": {
      "@/*": ["./src/*"]
    }
  }
}
```

验收：

```bash
pnpm exec vue-tsc --noEmit
```

### 15.8 Lightning CSS 报 `@theme`

现象：

```text
[lightningcss minify] Unknown at rule: @theme
```

原因：项目使用 UnoCSS，不是 Tailwind CSS v4 官方编译链；CSS 中的 `@theme inline` 没有被消费，原样进入最终 CSS 后被 Lightning CSS 识别为未知 at-rule。

处理：主题 token 维护在 `uno.config.ts` 的 `theme` 中，删除源码 CSS 里的 `@theme inline` 块。

验收：源码和构建产物中不再出现未消费的 `@theme`。

### 15.9 Lightning CSS 报属性选择器值非法

现象：

```text
[lightningcss minify] Invalid value in attribute selector
[data-spacing=0]
```

原因：`data-[spacing=0]` 这类 Tailwind 风格 data variant 生成了未加引号的数字属性值，Lightning CSS 严格解析时要求属性值加引号。

处理：在 UnoCSS 配置层使用 variant 修正 selector 生成，把属性选择器输出为：

```css
[data-spacing="0"]
```

验收：保留组件里的 `data-[spacing=0]:...` 类名，构建 CSS 中对应 selector 使用带引号属性值。

### 15.10 HAP 未签名

现象：

```text
WARN: Will skip sign 'hos_hap'. No signingConfigs profile is configured in current project.
```

产物表现：

```text
entry-default-unsigned.hap
```

原因：`build-profile.json5` 没有可用的 `signingConfigs`，或 `products[].signingConfig` 没有指向对应配置。

处理：按“build-profile.json5 标准配置”和“签名材料”章节补齐签名配置。

验收：产物为：

```text
entry-default-signed.hap
```

### 15.11 签名密码长度错误

现象：

```text
The length of the storePassword or keyPassword field in the signature configuration is less than 32
```

原因：Hvigor 签名配置中的 `storePassword` / `keyPassword` 使用了明文密码。

处理：使用 DevEco/Hvigor 加密后的密码字段，并保证它与 `signature/material/` 成套。

验收：SignHap 阶段不再报密码长度错误。

### 15.12 缺少 `signature/material`

现象：

```text
ENOENT: no such file or directory, stat '.../signature/material'
```

原因：Hvigor 解密 `storePassword` / `keyPassword` 时，会在 `storeFile` 同级目录查找 `material/fd`、`material/ac`、`material/ce`。

处理：签名材料目录保持完整：

```text
signature/
├── OpenHarmony.p12
└── material/
    ├── ac/material
    ├── ce/material
    └── fd/*/material
```

验收：SignHap 阶段可以读取并解密签名密码。

### 15.13 证书链错误

现象：

```text
Profile cert must a cert chain
Certificate format is in correct
verify certificate chain failed
```

原因：`certpath` 指向了单个证书，而签名工具需要完整应用证书链。

处理：`certpath` 指向完整证书链文件：

```text
signature/OpenHarmonyApplication.pem
```

验收：SignHap 阶段不再报 cert chain 相关错误。

### 15.14 ArkTS 可能抛异常 warning

现象：

```text
ArkTS:WARN ... Function may throw exceptions. Special handling is required.
```

原因：ArkTS 对 `getMainWindowSync`、`setWindowLayoutFullScreen`、WebView delegate、节点增删等可能抛异常 API 做静态检查。

处理：项目代码中的生命周期调用用 `try/catch` 包裹；依赖内 warning 优先通过升级 `@ohos-rs/ability` 处理。

验收：`CompileArkTS` 阶段无项目源码 warning；依赖 warning 若复现，记录依赖版本并按上游修复或可重复补丁处理。

### 15.15 Cargo patch warning

现象：

```text
unused field in patch for `tauri-utils`: `features`
patch `wry ...` was not used in the crate graph
```

原因：`[patch.crates-io]` 不消费 `features` 字段；未命中的 patch 会被 Cargo 标记为 unused。

处理：`features` 放在实际 dependency 上；未命中的 patch 从 `Cargo.toml` 移除。

验收：Cargo 编译阶段不再输出 patch warning。

### 15.16 `@ohos-rs/ability` 提示 `module.json` 不存在

现象：

```text
@ohos-rs/ability/src/main/module.json does not exist. This library will not be merged.
```

原因：`@ohos-rs/ability` 是 ArkTS 辅助包，当前包结构不按普通可合并 module 提供 `module.json`。该提示来自 Hvigor 的库合并检查。

处理：保持 `entry/oh-package.json5` 使用当前验证过的版本：

```json5
"@ohos-rs/ability": "0.4.0-beta.7"
```

验收：`CompileArkTS`、`PackageHap`、`SignHap` 均成功，最终生成 `entry-default-signed.hap`。

### 15.17 `oh_modules` 重新安装后依赖补丁丢失

现象：删除 `src-tauri/gen/ohos/oh_modules` 或重新执行 OHPM 安装后，依赖包源码恢复，ArkTS warning 可能重新出现。

原因：`oh_modules` 是安装产物，不是稳定源码入口。手工修改安装产物只影响当前工作区缓存。

处理：短期按 warning 指向文件重新确认 `@ohos-rs/ability` 版本和异常处理；长期将依赖修复上游化，或固化为可重复的本地 HAR / 补丁脚本。

验收：重新安装 OHPM 依赖后执行 `pnpm --dir apps/tauri harmony:build`，`CompileArkTS` 阶段通过，HAP 仍为 signed 产物。

## 16. 接入清单

按顺序执行并验收：

1. 安装 OpenHarmony 版 Tauri CLI。
2. 执行 `cargo tauri ohos -h`，确认存在 `init`、`dev`、`build`。
3. 配置 `package.json` 的 `harmony:*` 脚本。
4. 配置 `src-tauri/Cargo.toml` 的 OpenHarmony 分支依赖和 patch。
5. 按 `target_env = "ohos"` 隔离 Rust 插件依赖和插件注册。
6. 配置 `src-tauri/capabilities/default.json`。
7. 配置 `src-tauri/capabilities/ohos.json`。
8. 配置 `src-tauri/tauri.conf.json`。
9. 确认 `src-tauri/tauri.conf.json` 的 `bundle.android` 与当前 Tauri schema 兼容；默认只保留 `minSdkVersion` 和 `versionCode`。
10. 执行 `pnpm --dir apps/tauri harmony:init`。
11. 配置 `src-tauri/gen/ohos/entry/oh-package.json5`。
12. 配置 `EntryAbility.ets`。
13. 配置 `build-profile.json5`。
14. 放置 `signature/` 签名材料。
15. 执行 `pnpm --dir apps/tauri harmony:build`。
16. 验收 `entry-default-signed.hap`。
